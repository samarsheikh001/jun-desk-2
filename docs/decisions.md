## Decision log

- **2026-10-08 — D-40 — Page actions over WebMCP (AI-21), built now as v1.1.** The user brought a proposal for actions the agent can pick from: each page, or part of a page, registers what can be done right here (site-wide, per page, per element), the agent chooses only from that list, missing details are asked for with UI generated from the params, a risk level decides auto / confirm / human, the action runs in the visitor's browser, Done with Undo. Reviewed against the project: unlike D-39's page map nothing touches the host page unless the host's code opts in, and actions run with the visitor's own session, so hosts write a function instead of an endpoint and a secret. Decided: (1) the contract is WebMCP (Chrome's imperative `document.modelContext` tools; declarative `<form toolname>`), not a Jun-only API, so one investment by the host serves Chrome's agent and ours and we inherit the docs; the loader polyfills `document.modelContext` where absent and defers to native where present; Jun extras (`pages`, `key`, `element`, `undo`, `context`, `available`) live only in our registry via `JunDesk.registerAction`, a superset. (2) First version: code-registered actions in full; declarative forms only where Chrome supports them natively; our own form filling deferred (D-39's line). (3) AI-06 folds in as the `confirm` risk level (the default; `consequentialHint` maps to it) and W-09 as the param UI generated from a tool's input schema. (4) Server shape: a chosen browser action ends the AI turn, the widget runs it and sends the result, which the next turn reads; the DO never awaits the browser. (5) Built before launch, while M8 waits on the public repo and video; sites that register nothing are unaffected. AI-22 (GUI fallback, from reviewing Alibaba's Page Agent) stays `later` below it. Spec churn is tracked in CLAUDE.md "WebMCP conventions".
- **2026-10-09 — D-41 — The widget frame runs on Preact; the dashboard stays on React.** The island took about 2.5 s to appear on limoni.io, most of it loading the chat frame: about 92 KB of JS gzipped, of which React DOM was about 60 KB (measured from a source-mapped build; the rest is the chat itself, nothing dashboard-only). The user chose to move the frame to Preact (`preact/compat`, aliased in the build) over splitting out unused launchers (about 8 KB) or trimming shared CSS. The frame's JS went from about 92 KB to about 30 KB gzipped, the CSS is unchanged (16 KB). How: `widget.html` is its own Vite environment (`widget`, built after the Cloudflare plugin's client build into the same folder), where a plugin resolves `react`, `react-dom` and the JSX runtime to Preact; the dashboard build has `index.html` only. Trade-off: `vite dev` serves both pages from one module graph, so the frame runs on React in dev and the e2e suites; widget changes are also checked on a built version (`vite preview`, which runs the built Worker and assets). Preact 10 (`preact/compat` covers the React 18/19 APIs the widget uses); the widget code itself still imports from `react`.
- **2026-10-10 — D-42 — The model's decisions are tool calls, not control lines in its text.** The reply used to carry `HANDOFF: <reason>` (first line), `ESCALATE: <summary>` (last line) and `FOLLOWUPS: q | q`, found by parsing the text and held back from the stream while a line might become one. Workers AI's Mistral put `HANDOFF:` mid-reply ("I'm sorry, I can't do that for you. HANDOFF: …"): the visitor saw the internal line and nothing was handed off. The user asked for the proper fix rather than searching the text harder. Decided: `handoff({ reason })` and `flag_problem({ summary })` (offered only with debug context), read from the response's tool calls (`runAgent`, `replyOutcome` in `worker/ai/agent.ts`); the outcome shape is unchanged, so the Conversation object, evals and widget are too. Handoff has no `execute` (the call ends the turn, like a page action). Flagging runs, because Mistral doesn't reliably write text and call a tool in one response: the model flags first and explains in the next step, and a step that already explained ends the loop (otherwise Mistral wrote its whole reply again). Words written before a handoff stay as the AI's message, then the notice. Nothing is held back from the stream any more. `tools/<name>.yaml` can't take the built-in names. E2E on ChatGPT and Workers AI: chat, AI, debug, agent and page actions pass; no reply contains a control string. Follow-up questions were never produced in production with the old line (0 of 303 AI replies), and a `suggest_followups` tool wasn't called either (0 of 31 e2e replies, both providers); the user chose to have them written by a separate fast job instead (`followups`, AI-16's list): after an answer that used the knowledge is saved, one small call writes up to 3 questions from the question, the answer and its sources, and they're added to the message in place, a moment after the answer.
- **2026-10-10 — D-43 — Widgets (W-09) in v1, in OpenAI's ChatKit widget format, with our own template engine and renderer.** The user looked at Chatbase's new Widgets (a builder for cards the bot shows: AI builder, JSX-like code, Zod schema, functions, states; observed in their dashboard 2026-10-10) and ChatKit Studio (widgets.chatkit.studio), and asked for widgets now rather than in v2. What's open: the format (component names and props in openai/chatkit-python `chatkit/widgets.py` and openai/chatkit-js `widgets.d.ts`, both Apache-2.0); OpenAI's renderer is not (chatkit.js on their CDN is a loader for an iframe they host). @swis/genui-widgets (MIT, Vue 3) renders ChatKit JSON but needs Vue and nunjucks, which compiles templates with `new Function` and can't run on Workers. Decided: `widgets/<name>.widget` is ChatKit Studio's Download as is (`version: "1.0"`, `template`: a Jinja template that renders the component tree's JSON, plus `jsonSchema` and the Studio's `encodedWidget` / `outputJsonPreview`; our optional `sample` for previews); `widget: <name>` on a `tools/*.yaml` shows a successful JSON result as that card. Our own pieces: `shared/jinja.ts` (the Jinja subset the Studio compiles to, with filters and tests, step and size limits, no eval), `shared/widgets.ts` (file parsing, render, tree check: known components only, ≤ 400 nodes, ≤ 48 KB), `web/widget/chatkit/` (Preact renderer after genui-widgets' structure, our tokens, our own icons, https images only, CSS values checked). The data comes from the tool's whole response, never from the model; the model gets the picked output plus a note that the customer sees a card. The card rides on the tool's finished step (live) and is saved as `meta.widgets`. Buttons, a Form's submit and Card confirm/cancel send a visitor message (the button's label) with `meta.widgetAction` (card, action type, payload, the card's own field values); the Conversation object checks the action against the card it showed (forged or repeated presses are refused) and marks the card used; the AI's next turn reads it as one line (`widgetActionLine`). Not built: ChatKit's client-handled actions, `onChangeAction`, `Transition` animations; actions don't call tools directly (the AI decides). Agents see the card in the inbox and preview widget files on the Agent page; evals report cards shown and can `expect.widget`. E2E: `scripts/e2e-widgets.ts`.

Worth reporting upstream.

- **2026-10-05 — D-23 — Visitors and identity (M6, user: "letsgo").**
  - **Identity (V-03):** the host app's backend signs a short-lived **HS256 JWT** (`sub` required, `exp` required, optional `email`, `name`, `attributes`) with a per-workspace identity secret (Settings → Install; admins can show, rotate or turn it off). Only HS256 is accepted, never `none` or a key from the token. Rotating the secret revokes all tokens. The page passes it with `data-user-token` or `JunDesk.identify(jwt)`; `JunDesk.logout()` forgets it. Asymmetric keys (RS256/JWKS) can come later if customers ask.
  - **Merge (V-04):** browsers hold visitor tokens in a new `visitor_tokens` table (one contact, many browsers). An anonymous visitor who identifies merges into the user's contact (conversations and tokens move). A browser already identified as another user gets a fresh token instead, so one user never inherits another's history (shared computers).
  - **Attributes (V-05):** come only from the verified JWT (`attributes` claim) and replace the previous ones on each identify. The AI's prompt names a verified customer; tools can use `{user.id}`, `{user.email}`, `{user.name}`, `{user.<attribute>}` and refuse ("not signed in") for anonymous visitors. Unverified attributes from page JavaScript are not accepted in v1.
  - **Live visitors (V-01):** the loader opens one WebSocket (`/api/widget/:key/live`, any origin) to the workspace hub, which hibernates between messages. It reports page, title, referrer, session start, language and time zone; Cloudflare adds country and city. Sessions live in sessionStorage. Agents get the full list on connect, then changes. Visitor sockets never receive inbox events.
  - **Agent-started chats (V-07):** an invite (stored in `visitor_invites`, 30 min, single use) is delivered to that session's page as a card with the agent's name. Replying creates a conversation that starts with the agent's message, handled by humans and assigned to that agent.
  - **Consent (V-06):** `data-consent="required"` stores nothing (no sessionStorage, chat token in memory only) and opens no live connection until `JunDesk.consent(true)`.
  - **Loader size:** with this the readable `public/widget.js` grew past 5 KB gzipped, so the build now minifies it (`rolldown/utils`, Vite's own dependency): 4.05 KB gzipped served.
- **2026-10-05 — S-11 — The nudge is worded by the AI, not guessed from URL keywords.** The user asked how the widget "knew" a failure was a payment: it matched words like `pay`/`billing`/`card` in the URL, which mislabels e.g. `/api/cards`. - **2026-10-05 — T-16 — Widget domain allowlist (user: "letsgo").** The widget key is public, so copies of the snippet could embed your chat elsewhere, add fake sessions to the live list and spend AI on nudges. Admins list allowed websites; browsers enforce it: the live socket and the nudge check `Origin`, and the chat frame carries `Content-Security-Policy: frame-ancestors` for the listed sites (both `http` and `https`, any port).
